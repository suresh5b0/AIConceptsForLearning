Forward Deployed Engineer

A Forward Deployed Engineer (FDE) is the hands-on AI builder who works closest to real customer problems. Instead of only designing models in theory, an FDE translates business pain into working AI solutions, prototypes them fast, and helps ship them into production.

What an FDE does

  • Meet with customers or teams to understand high-value pain points.
  • Identify where AI can create measurable business impact.
  • Prototype quick solutions using LLMs, APIs, workflows, and data pipelines.
  • Integrate AI with real tools, systems, and enterprise workflows.
  • Ship production-ready solutions with monitoring, evaluation, and guardrails.

Why the role matters

  • AI projects often fail because of unclear requirements or weak deployment.
  • FDEs bridge the gap between technical capability and business value.
  • They combine engineering, product thinking, and customer communication.
  • They help teams move from demo to durable operational systems.

LLMs

Large Language Models

What are LLMs?

LLMs are AI models trained on huge amounts of text so they can understand questions, write text, summarize content, and help with many language tasks.

How LLMs work

They learn patterns in language and predict the next word or token. This helps them generate useful responses, explanations, and code.

Why do we use LLMs?

We use LLMs because they can save time, automate repetitive writing tasks, support customer service, help developers, and make information easier to search.

Simple examples

Example: an LLM can summarize a long report, answer a question about company policy, or generate a Python function from a request.

Why LLMs are useful

  • They understand natural language, so people can interact with them easily.
  • They can help with writing, learning, coding, and brainstorming.
  • They can be connected to tools, documents, and workflows for smarter applications.
  • They can be used in chatbots, assistants, search systems, and automation tools.

How it works when you type a query in a chat window

When a user sends a message, the system follows a short flow to produce a response.

  1. Read the question: The model receives your text input.
  2. Understand the intent: It tries to understand what you want.
  3. Use its training and context: It uses patterns learned during training and any recent chat context.
  4. Generate an answer: It predicts a helpful response word by word.
  5. Return the reply: The final answer is shown in the chat window.

In short: question → understanding → response generation → chat reply.

Easy examples of LLM usage

  • Student: Ask for a simple explanation of neural networks.
  • Developer: Ask for a Python script to read a CSV file.
  • Business: Ask for a summary of meeting notes and action items.
  • Support team: Use an LLM to answer common questions from documentation.

LLM Best Practices

  • Context windows: Be mindful of token limits and keep prompts concise.
  • Costs: Estimate inference and embedding costs — batch requests and cache where possible.
  • Local vs Hosted: Use hosted APIs for scalability; prefer local quantized models for privacy and offline use-cases.
  • Instruction Tuning: Apply instruction-tuning or adapters for consistent behaviors across tasks.
  • Evaluation: Use automated metrics (BLEU, ROUGE, F1) plus human evals for quality checks.
  • Safety: Add filters, rate-limits, and content policies before deployment.
RAG

Retrieval-Augmented Generation

What is RAG?

RAG enriches generation with retrieved context from documents or knowledge stores.

Why use RAG?

It reduces hallucinations and improves relevance for factual, up-to-date answers.

RAG Step-by-Step

RAG works in simple stages: bring in knowledge, find the right pieces, and use them to answer.

  1. Data ingestion: Collect documents such as PDFs, websites, notes, or database records.
  2. Clean and organize: Remove irrelevant text, fix formatting, and prepare the content.
  3. Split into chunks: Break long documents into smaller pieces so retrieval is more accurate.
  4. Create embeddings: Turn each chunk into a vector using an embedding model.
  5. Store in a vector database: Save the vectors along with useful metadata like source and title.
  6. Receive a user question: The user asks something that needs an answer.
  7. Find similar content: Convert the question into a vector and search the database for the closest matches.
  8. Send context to the LLM: Give the retrieved chunks to the model as extra context.
  9. Generate the final answer: The LLM answers using the retrieved information and can cite the source.
  10. Improve over time: Review results, adjust chunk size, and refine retrieval quality.

Vector Databases and Retrieval

Vector databases store embeddings and support fast similarity search for semantic retrieval, FAQ bots, and knowledge assistants.

  • Why they matter: They let you search by meaning rather than exact keywords.
  • Common options: Pinecone, Weaviate, Milvus, Chroma, pgvector, and Azure AI Search.
  • Key features: Metadata filters, hybrid search, reranking, and approximate nearest neighbor indexes.
  • Best practice: Keep chunk size small, store useful metadata, and refresh embeddings when content changes.

RAG Approach in Practice

A production RAG system usually combines retrieval, ranking, prompt construction, and evaluation.

  • Simple RAG: Retrieve top-k chunks and append them to the prompt.
  • Advanced RAG: Add reranking, citation checks, chunk metadata, and query rewriting.
  • Agentic RAG: Let an agent decide when to search, which tools to use, and how to verify results.

Improving RAG Quality

  • Chunking strategy: Choose chunk sizes that balance context and precision (commonly 200–800 tokens).
  • Embedding selection: Use an embedding model aligned with your domain for better semantic matches.
  • Reranking: Combine ANN retrieval with lightweight rerankers or cross-encoders to boost final relevance.
  • Metadata & filters: Store source, date, and type; use filters to reduce noisy matches.
  • Hybrid search: Mix keyword (BM25/Elasticsearch) + semantic search for precise retrieval.
  • Citation & provenance: Attach source snippets and links in generated answers to increase trust and auditability.
  • Latency: Cache frequent queries, use async retrieval, and tune vector DB indexing.

Realtime RAG

Realtime RAG updates retrieval results as new documents arrive and can stream answers while keeping them grounded.

  • Use live ingestion for current documents and logs.
  • Refresh embeddings automatically on data changes.
  • Stream partial answers to users while retrieval continues.
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class QueryRequest(BaseModel):
    query: str

@app.post("/query")
def query_knowledge(body: QueryRequest):
    docs = vector_store.search(body.query, top_k=4)
    context = "\n\n".join([doc.text for doc in docs])
    prompt = f"Use the facts below to answer the question:\n\n{context}\n\nQuestion: {body.query}"
    answer = llm.generate(prompt)
    return {"answer": answer}

Realtime RAG Use Cases

  • Customer support: Answers questions using the latest help articles and product updates. Why RAG? It gives fresh, accurate answers without retraining the model.
  • Operations monitoring: Explains alerts and logs from live systems. Why RAG? It pulls current incident details and helps teams respond faster.
  • Sales assistant: Finds current pricing, inventory, and policy information. Why RAG? It ensures the assistant uses the latest business data.
  • HR chatbot: Answers policy questions from employee handbooks and internal documents. Why RAG? It keeps responses grounded in approved company knowledge.
  • Legal or medical search: Retrieves relevant documents for review. Why RAG? It improves accuracy by grounding answers in trusted sources.

Why we use RAG in real-time systems

RAG is useful when the answer must be based on current or private information.

  • It reduces hallucinations by giving the model real retrieved context.
  • It allows updates without retraining the model every time content changes.
  • It works well for chatbots, search tools, support systems, and internal knowledge assistants.

RAG vs Fine-Tune Comparison

Aspect RAG (Retrieval-Augmented Generation) Fine-Tuning
How it works Retrieves external documents at runtime and passes them as context to the model. Modifies model weights offline using labeled training data.
Model changes Model stays unchanged; only context is added. Model weights and parameters are permanently updated.
Update frequency Can add new documents anytime without retraining. Requires retraining to incorporate new knowledge.
Cost Lower cost (vector storage + retrieval). Higher cost (compute, GPU time, data labeling).
Latency Slightly higher (retrieval + generation). Lower (only generation phase).
Data needed Documents, no labeling required. Labeled input/output pairs.
Best for Up-to-date knowledge, large document sets, Q&A systems. Task-specific style, consistent behavior, specialized domains.
Hallucination risk Lower (grounds answers in retrieved docs). Higher (model may generate plausible but false outputs).

When to Use RAG

  • You have a large knowledge base that changes frequently.
  • You need factual accuracy and want to reduce hallucinations.
  • You want minimal computational overhead and faster deployment.
  • Your documents are already available (no labeling needed).

When to Use Fine-Tuning

  • You need a specialized model for a specific task or domain.
  • You have labeled training data and consistent patterns.
  • You need lower latency or offline inference.
  • You want the model to learn a particular response style or format.

How to Fine-Tune

Fine-tuning adapts an existing model using labeled examples or a domain-specific dataset.

In simple words: start with a strong pre-trained model, teach it with examples, and then use the updated version for your task.

  • Step 1: Choose a base model that matches your task, such as a text generation or classification model.
  • Step 2: Collect and format training data with input/output pairs, such as CSV, JSONL, or a dataset object.
  • Step 3: Tokenize your data with the model tokenizer and prepare training and validation splits.
  • Step 4: Set training settings like batch size, learning rate, number of epochs, and evaluation strategy.
  • Step 5: Train the model using a Trainer or fine-tuning API, then test it on sample examples.
  • Step 6: Save the fine-tuned model, upload it to a model hub, or deploy it in an app.

What changes after fine-tuning? The model becomes better at your specific style, task, or domain, but it does not automatically learn new facts unless you retrain it with updated data.

Important note: Fine-tuning needs good quality data. If the examples are noisy or inconsistent, the model may learn the wrong pattern.

from datasets import load_dataset
from transformers import AutoTokenizer, AutoModelForSeq2SeqLM, TrainingArguments, Trainer

model_name = "google/flan-t5-base"
dataset = load_dataset("csv", data_files={"train": "data/train.csv", "validation": "data/valid.csv"})

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForSeq2SeqLM.from_pretrained(model_name)

def preprocess(example):
    inputs = tokenizer(example["input_text"], truncation=True, padding="max_length", max_length=256)
    targets = tokenizer(example["target_text"], truncation=True, padding="max_length", max_length=128)
    inputs["labels"] = targets["input_ids"]
    return inputs

dataset = dataset.map(preprocess, batched=True)

training_args = TrainingArguments(
    output_dir="./fine-tuned-model",
    evaluation_strategy="epoch",
    learning_rate=2e-5,
    per_device_train_batch_size=8,
    per_device_eval_batch_size=8,
    num_train_epochs=3,
    save_total_limit=2,
    load_best_model_at_end=True,
)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=dataset["train"],
    eval_dataset=dataset["validation"],
)

trainer.train()
trainer.save_model("./fine-tuned-model")

Prompt Engineering Guide

What Is a Prompt?

A prompt is the input you give to an AI model.

Why Prompt Engineering Matters

LLMs generate outputs based on the instructions they receive.

Think of prompting like giving directions:

  • Vague directions → unclear result
  • Clear directions → better result
Prompt:
Write an essay.

Result:

  • Unclear topic
  • Unclear length
Write a 300-word essay about climate change for high school students.

Result:

  • Specific topic
  • Specific audience
  • Specific length

3. Anatomy of a Good Prompt

A strong prompt often contains:

1. Role

You are an experienced AI teacher.

2. Task

Explain neural networks.

3. Context

The audience is beginners who know basic Python.

4. Format

Use bullet points and examples.

Formula:

Role + Task + Context + Format

Assume they know basic mathematics.

Use simple language and examples.

4. Zero-Shot Prompting

The model receives instructions without examples.

Translate this sentence into Spanish:
I love learning AI.

This is called: Zero-shot Learning.

5. One-Shot Prompting

You provide one example.

Input: Dog
Output: Animal

Input: Rose
Output:

The model learns the pattern from the example.

6. Few-Shot Prompting

You provide several examples.

Input: Dog
Output: Animal

Input: Rose
Output: Plant

Input: Eagle
Output:

This technique often improves reliability.

7. Chain-of-Thought Prompting

Solve this math problem step by step.

This often improves reasoning quality and is useful for learning.

8. Structured Prompting

Explain machine learning using:

1. Definition
2. Example
3. Advantages
4. Disadvantages

The output becomes easier to read.

9. Constraint-Based Prompting

Explain AI in fewer than 100 words.
Use language suitable for a 12-year-old.

Constraints help control outputs.

10. Prompt Chaining

Break a large task into smaller prompts.

Step 1:
Generate startup ideas.

Step 2:
Select the best idea.

Step 3:
Create a business plan.

This is commonly used in AI workflows and agents.

11. Prompting for Coding

Write a Python function that finds the largest number in a list.

Requirements:
- Use type hints
- Add comments
- Include an example

Specific prompts generally produce better code.

Constraints:

Multi-Agent Patterns & Coordination

Multi-agent systems coordinate specialized agents to solve larger tasks. Common patterns:

  • Coordinator pattern: A central orchestrator assigns tasks to worker agents and aggregates results.
  • Blackboard pattern: Agents publish findings to a shared space (blackboard) where others can read and act.
  • Pipeline pattern: Agents form stages of a pipeline (search → analyze → summarize).
  • Peer negotiation: Agents negotiate roles, trade information, and resolve conflicts when overlapping tasks occur.
  • Planner-Worker-Critic pattern: One agent creates a plan, specialists execute tasks, and a reviewer checks quality before final response.
  • Router pattern: A dispatcher classifies the request and sends it to the most suitable specialist agent.

Design considerations: clear interfaces, retry/timeout policies, idempotent tool calls, shared memory boundaries, budget limits, and centralized logging for traceability.

Multi-Agent Design Principles

  • Role specialization: Give each agent a narrow responsibility such as research, coding, validation, or summarization.
  • Shared state: Keep a common context object so agents can coordinate without duplicating or overwriting each other's work.
  • Explicit handoff: Define inputs, outputs, and acceptance criteria for each agent handoff.
  • Conflict handling: Add disagreement resolution, retries, or escalation paths when agents produce different answers.
  • Cost and latency controls: Limit excessive agent loops, tool calls, and token usage with budgets and timeouts.
  • Observability: Log every prompt, tool call, and decision to debug failures and improve reliability.

AI Agents in Practice

  • Customer Service Agent: Handles inquiries, accesses FAQs, and escalates complex issues.
  • Data Analyst Agent: Queries databases, performs calculations, and generates reports.
  • Software Development Agent: Writes code, runs tests, and fixes bugs based on requirements.
  • Personal Assistant Agent: Manages schedules, sends emails, and provides recommendations.
  • Research Agent: Gathers information from various sources, summarizes findings, and identifies key insights.

How AI agents work

An AI agent usually follows a loop of perception, reasoning, action, and observation. The model reads the user request and current context, decides what to do next, uses the right tool or data source, and then evaluates the result before continuing. This loop keeps going until the task is complete or a stop condition is reached.

  1. Goal: The agent receives a task such as "research this topic and draft a summary".
  2. Context: It gathers current inputs, memory, system instructions, and available tools.
  3. Planning: It decides whether to search, calculate, retrieve data, or ask for clarification.
  4. Action: It calls the relevant tool or external system to perform the work.
  5. Observation: It reads the result and decides whether the task is complete or needs another step.
  6. Response: It produces the final answer or takes the next action with the new information.

Why agents are needed

Agents are useful when a task is too complex for a single prompt or a simple chatbot. They help automate multi-step work that needs decisions, data retrieval, tool use, and iterative refinement. Instead of asking an LLM for one answer, an agent can carry out a job from start to finish.

  • Real work is multi-step: research, fetch data, validate facts, and produce a final result.
  • Tools extend the model: search, databases, code execution, APIs, and file operations create real capability.

Agentic AI

Agentic AI is the next step beyond simple agents: it combines planning, memory, tool use, and multi-agent orchestration to solve more complex, real-world problems. It emphasizes autonomous decision-making and adaptive behavior.

Autonomous Decision-Making

Agents independently decide actions based on goals, observations, and available tools, adapting to dynamic environments.

Adaptive Learning & Memory

Agents learn from past interactions, store relevant information, and retrieve knowledge to improve future performance and decision-making.

Complex Task Orchestration

Break down intricate problems into manageable sub-tasks, coordinate actions, and synthesize results from multiple tools or sub-agents.

Tool Integration & Extension

Seamlessly incorporate diverse external tools (APIs, databases, web search) to expand capabilities and interact with the real world.

Proactive Problem Solving

Agents can anticipate issues, proactively seek solutions, and execute multi-step plans without constant human intervention.

Human-in-the-Loop Design

Implement mechanisms for human oversight, feedback, and intervention to ensure safety, ethical alignment, and performance tuning.

Agentic AI Learning Track

  1. Build a simple LLM-based assistant first.
  2. Add retrieval from documents or a knowledge base.
  3. Integrate one tool, such as search or a calculator.
  4. Add memory for user preferences and recent tasks.
  5. Enable the agent to plan and revise multiple actions.
  6. Experiment with multiple agents collaborating on a shared goal.

Advanced Agentic Concepts

  • Self-Correction: Agents identify and rectify their own mistakes or inefficient actions.
  • Multi-Agent Systems (MAS): Designing and orchestrating teams of agents with specialized roles to achieve common goals.
  • Cognitive Architectures: Building agents with human-like cognitive functions like perception, attention, and reasoning.
  • Emotional AI: Developing agents that can understand, interpret, and respond to human emotions (ethically and safely).
  • Emergent Behavior: Observing complex, unprogrammed behaviors arising from simple agent interactions within a system.

How an agentic system is usually built

A practical agentic system usually combines a few layers instead of relying on one prompt or one model call. The most important pieces are context, planning, tool use, memory, and validation.

  • Input and context: the user request, current state, instructions, and any structured data available to the agent.
  • Planning layer: the agent decides what to do next, what the next sub-goal is, and whether it needs more information.
  • Tool execution: the agent calls tools such as search, code execution, APIs, databases, file access, or workflow triggers.
  • Memory layer: short-term memory helps with the current task, while long-term memory stores user preferences, summaries, and prior events.
  • Evaluation and feedback: the agent checks whether the result satisfies the goal, then decides whether to continue, retry, or stop.
  • Guardrails: filters, policies, validation, and approvals help prevent bad or unsafe actions.

When to use an agent instead of a simple workflow

Use a direct workflow when the task is predictable and linear. Use an agent when the job needs decisions, iteration, tool use, and adaptation.

  • Simple workflow: fetch data, transform it, send it to a model, return a response.
  • Agentic flow: gather context, decide what to search, call tools, validate outputs, revise steps, and decide the final action.
  • Use agents when: the task is multi-step, context changes often, decisions depend on tool results, or human approval is needed at checkpoints.
  • Use deterministic workflows when: the process is fixed, auditable, and should not improvise.

Common failure modes in agentic AI

Agentic systems can be powerful, but they also fail in predictable ways. Learners should watch for these issues early.

  • Tool overuse: the agent calls too many tools or loops without converging.
  • Bad context selection: it ignores relevant files or chooses weak retrieval results.
  • Prompt drift: the agent slowly changes behavior because instructions are too vague or inconsistent.
  • Weak validation: the model returns an answer that looks good but is incorrect or unsupported.
  • Unsafe actions: the agent performs a high-impact operation without approval or policy checks.
  • State confusion: memory or session state causes incorrect assumptions across tasks.

Good guardrails include clear success criteria, structured tool outputs, trace logs, rate limits, validation steps, and human review for sensitive actions.

n8n: Workflow Automation with AI

n8n is a low-code workflow automation platform that connects apps, APIs, databases, AI models, and event triggers in a visual way. It is especially useful for AI projects because it lets you build pipelines that fetch data, call LLMs, process responses, store state, and trigger actions without writing every step from scratch.

What n8n is

  • Best for: automation, integrations, chat agents, triggers, API chains, and AI workflows.
  • Main idea: connect nodes that represent triggers, actions, tools, and logic.
  • Strengths: easy visual design, reusable workflows, strong integrations, and flexible AI orchestration.
  • Typical use cases: email automation, CRM updates, AI support workflows, data processing, ticket routing, and webhook-driven agents.

Why teams use n8n

  • Build AI automations faster than custom code-only solutions.
  • Connect internal tools and external services without custom glue code.
  • Use AI as part of a real workflow, not just a standalone chat app.
  • Store and route data between systems with clear logic and monitoring.

Core n8n concepts

  • Workflow: a full automation script made of connected nodes.
  • Trigger: the event that starts the workflow such as webhook, cron, email, or chat message.
  • Node: a single action or logic block like HTTP Request, OpenAI, IF, Set, Code, or Database.
  • Credential: securely stored authentication such as API key, OAuth token, or database login.
  • Execution: each run generates logs, inputs, outputs, and error states for debugging.
  • Memory: workflow state, conversation context, or persisted data used across steps or retries.

How AI agents work in n8n

n8n lets you build an agent-like flow where one node receives the user request, another fetches context, another calls a chat model, and a final node triggers a business action such as sending an email, updating a database, or creating a ticket.

  1. Receive input: webhook, chat form, or user message starts the workflow.
  2. Collect context: fetch documents, database rows, or previous conversation history.
  3. Call a model: use an LLM node to summarize, classify, reason, or generate a response.
  4. Process output: clean the answer, validate it, or pass it to a decision node.
  5. Take action: update a CRM, send an email, create a task, or return a response to the user.
  6. Store memory: save the interaction or some structured state for future tasks.

  • Dockerfile: a script that defines how to build an image.
  • Registry: a place to store and share images, such as Docker Hub or Azure Container Registry.
  • Compose: a tool for running multi-container applications with a single YAML definition.

  • Runs LLM services and APIs the same way in dev and production.
  • Isolates Python environments, vector databases, and model runtimes.
  • Makes it easier to share reproducible setups with teammates.
  • Supports multi-service stacks such as app + database + UI + model runner.

LangGraph: Visual Workflow Design

LangGraph is a library for building stateful, multi-actor applications with LLMs. It extends LangChain with graph-based state management and deterministic workflows.

📊

Graph-Based States

Model workflows as directed graphs with nodes representing operations and edges representing state transitions.

🔄

Cyclic Workflows

Support feedback loops, retries, and iterative refinement within agent workflows.

🎯

Deterministic Execution

Replay, debug, and trace exact execution paths through complex agent logic.

🔍

Visualization

See your workflow as a visual graph during development and debugging.

Key Concepts

  • State: Shared data structure passed between nodes
  • Node: Function that processes state and returns updates
  • Edge: Connection between nodes with routing logic
  • Conditional Edges: Dynamic routing based on state
  • Cycles: Feedback loops for iterative refinement
  • Checkpointing: Save state snapshots for debugging
  • Streaming: Real-time output as graph executes

Simple Example

from langgraph.graph import StateGraph
from typing_extensions import TypedDict

# Define state
class AgentState(TypedDict):
    messages: list
    question: str
    answer: str

# Create graph
graph = StateGraph(AgentState)

# Define nodes
def query_node(state):
    # Process question
    return {"answer": "Processing..."}

def refine_node(state):
    # Refine answer
    return {"answer": "Refined answer"}

# Add nodes
graph.add_node("query", query_node)
graph.add_node("refine", refine_node)

# Add edges
graph.add_edge("query", "refine")
graph.set_entry_point("query")
graph.set_finish_point("refine")

# Compile and run
app = graph.compile()
result = app.invoke(
    {"messages": [], "question": "What is AI?"}
)

Advanced: Conditional Routing

Make workflow decisions based on state:

def should_refine(state) -> bool:
    """Check if answer needs refinement"""
    return len(state["answer"]) < 50

# Add conditional edge
graph.add_conditional_edges(
    "query",
    should_refine,
    {
        True: "refine",     # If refinement needed
        False: "complete"   # Otherwise complete
    }
)

# This creates a dynamic workflow that adapts based on state

Model Context Protocol

MCP Overview

MCP makes it easier to connect AI models and clients to external tools safely, reliably, and with consistent behavior.

Why MCP?

  • Standardize tool interfaces
  • Enable secure external access
  • Support reusable integrations
  • Simplify multi-client workflows

When to Use MCP

  • When AI needs external tool access
  • When multiple apps use the same tool set
  • When security and observability matter
  • When you want a protocol-driven agent ecosystem

MCP Inspector Tool

The MCP Inspector helps teams review registered tools, validate request and response schemas, and trace tool call lifecycle events.

  • Inspect tool manifests and supported operations.
  • Validate input/output schemas before deployment.
  • Replay tool calls using sample payloads.
  • Debug authorization, routing, and response formats.

How MCP Works

Model Context Protocol defines how a model client discovers tools, exchanges structured tool requests, and receives tool results in a consistent format.

  • Define tool capabilities with metadata, input schema, and output schema.
  • Register tools with a protocol server or gateway.
  • Send model-generated tool calls through the MCP connector.
  • Return tool outputs as structured context for the model to continue the workflow.
  • Support resources, prompts, and tools so a client can discover reliable capabilities before execution.

What are the External Tools in MCP?

In MCP, external tools are functions or services that an AI client can discover and call through a standard protocol. They are not part of the model itself; they are the bridges that let the model interact with real systems safely.

  • Search tools: Web search, documentation lookup, enterprise search, or internal knowledge retrieval.
  • Database tools: Query tables, fetch records, run summaries, or pull operational data.
  • API tools: Connect to CRMs, ticketing systems, billing tools, email services, or SaaS platforms.
  • File and document tools: Read PDFs, retrieve project files, upload documents, or edit structured content.
  • Calculator and logic tools: Perform numeric operations, validation, conversions, or rule checks.
  • Workflow tools: Trigger pipelines, approvals, automation, or backend jobs.
  • Monitoring tools: Fetch logs, alerts, health checks, and analytics data for troubleshooting.

These tools are exposed to the model through a manifest or protocol contract, which defines the name, supported inputs, output schema, and security requirements. That makes the tool discoverable and predictable for multiple clients.

How to Secure MCP

Security is critical because MCP enables model-driven access to business tools and data. Treat every tool as a privileged integration and enforce strict controls.

  • Least privilege: Only expose the exact tools, permissions, and data needed for the workflow.
  • Credential isolation: Store secrets in environment variables, managed secret stores, or cloud key vaults instead of embedding them in manifests or prompts.
  • Schema validation: Validate all inputs and outputs with strict JSON schemas and reject malformed or unexpected payloads.
  • Tool allowlisting: Restrict which tools can be called, which users can trigger them, and under what conditions.
  • Rate limiting and timeouts: Prevent runaway loops, repeated retries, and expensive or unsafe tool invocations.
  • Approval checkpoints: Require human confirmation before actions with high impact, such as writing files, sending emails, or changing production data.
  • Sandboxing: Run external tool execution in isolated environments with limited network, filesystem, and process access.
  • Audit logging: Track tool names, arguments, prompts, user identities, and outcomes for debugging, compliance, and incident response.
  • Prompt-injection defense: Do not trust raw model output as instructions. Validate tool arguments and keep tool execution separate from direct system-level commands.
  • Transport security: Use HTTPS, mutual TLS where needed, and signed configuration or manifests to reduce tampering risk.

Different ways to configure MCP

There is no single way to configure MCP. Teams usually choose a pattern based on where the tool is running, how it is exposed, and how much control they need over security and deployment.

  • Local stdio MCP server: Start a local process that speaks MCP over standard I/O. This is common for desktop tools, local dev, and private scripts.
  • HTTP/SSE remote MCP server: Run a server as a service and connect the client over HTTP or SSE. This is helpful for shared tools, internal services, and multi-user environments.
  • Client-managed tool registry: The client keeps a list of available MCP tools and the connection details for each tool server.
  • Gateway-based configuration: Put MCP behind a gateway that performs auth, rate limits, validation, and logging before forwarding requests to internal tools.
  • Environment-driven configuration: Store server URLs, tokens, and options in environment variables so the same setup works across dev, test, and production.

How to add a custom MCP configuration

Custom MCP is usually created by writing a server that exposes one or more tools, then registering it in the client configuration. This lets you model a business tool, internal API, or domain-specific service with a clear schema.

  1. Define the tool interface: Give each tool a name, description, input schema, and output schema.
  2. Implement the server: Accept request payloads, validate arguments, call the real function or API, and return structured output.
  3. Register the server: Add it to the client config with command, args, URL, auth, or local path.
  4. Test discovery: Verify the client can list tools and inspect metadata before using them.
  5. Audit and secure: Restrict tool permissions, enforce validation, and log each invocation.

Different tools require different connection settings. The main idea is the same: describe the tool clearly, pass any required auth or endpoint config, and keep the configuration secure.

  • Filesystem tools: specify allowed directories, read/write permissions, and safe file extension filters.
  • GitHub or ticketing tools: configure token-based auth, base API URL, repository filters, and action scopes.

2) Add Retrieval (RAG) to Improve Factuality

Goal: attach a small document store so the agent can fetch context before answering. This reduces hallucinations for domain-specific queries.

# Pseudo-Python (conceptual)
from vectorstore import InMemoryVectorStore
from llm_client import LLM

store = InMemoryVectorStore()
store.add('doc1', 'Python is a popular programming language')

llm = LLM(model='gpt-4o-mini')

def answer(query: str):
    hits = store.search(query, top_k=3)
    context = "\n\n".join([h.text for h in hits])
    prompt = f"Use the context below to answer:\n\n{context}\n\nQuestion: {query}"
    return llm.generate(prompt)
